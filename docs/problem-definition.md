# Problem definition (Part 4) — **locked**

> **North-star metric:** Wishlist-to-Purchase within 30 days (W2P 30d)
> **Constraint:** no monetary incentive as the core lever
> **Evidence in:** `Phase-1/data/discovery/` (895 raw → 150 normalized, 12 validated themes) and
> [`docs/research/`](./research/synthesis.md) (9 questionnaire responses, 28–31 Aug 2026)
> **Supersedes:** the working sketch in [problemstatement.md](./problemstatement.md) §4.1, and the
> Phase 2 nomination *FitSizeAnxiety → resolve*
> **Gates:** Phase 5 scope — see §7
> **Generated by:** `npm run phase4:lock` → `phase-4/data/` (`problem-definition.json`,
> `decision-tree.json`, `signals.json`, `report.html`). Every count below is computed from the
> artefacts, not typed by hand.

This document locks the problem. It is written **from the evidence**, and where the evidence
contradicts our earlier hypothesis it follows the evidence rather than the hypothesis.

---

## 0. What changed, and why the earlier frame did not survive

Phase 2 nominated **FitSizeAnxiety → resolve** (rank 1, score 0.873) from the scrape. Primary
research does not support fit as the *leading* barrier:

| Signal | Scrape said | Questionnaire says |
|---|---|---|
| Leading barrier | Fit/size, frequency 0.367 | Price 5/9 · quality 2/9 · fit **0/9** as the *main* reason |
| Fit as the unlock | High feasibility, rank 1 | **1/9** name fit information as the one thing that would unlock |
| Fit as a doubt | Frequency 0.367, impact high | **5/9** cite size/fit/appearance among their uncertainties — R02, R03, R07, R08, R09 |
| Wishlist clutter | WishlistDecay theme | **6/9** hold only 1–5 saves; 2/9 hold >50 |

Fit is real but **secondary** — a live doubt, rarely the deciding one. The scrape over-ranked it,
which is the expected failure mode of public reviews: people write about fit when a garment
disappoints them after delivery, which is a different moment from the one that blocks a purchase.

The honest read is not "fit instead of price". It is that **both are surface answers to the same
missing capability**, which §3 states as the root cause.

## 1. Target user segment

**The Stalled Shortlister.** A shopper who saves several items they genuinely like, returns to the
list, and leaves without deciding — because nothing in the list helps them finish a judgement.

| Attribute | Definition | Evidence |
|---|---|---|
| Saves and does not convert | Buys from saves *sometimes* or less | 5/9 (Q5); 9/9 have an unbought save (Q6) |
| Holds comparable options | ≥2 similar items saved, or actively compares before buying | 6/9 compare in-app (Q11); 4/9 save in order to compare (Q7) |
| Researches before deciding | Reads reviews or customer photos | 8/9 and 7/9 (Q11) |
| Low confidence | Unsure the item is right for them | Q9 mean 2.89, range 0–6 |
| **Not** a pure sale-watcher | Says price, but does not primarily *act* on sales | Only 2/9 "wait for a sale" as behaviour (Q11) |

**Revised from S2 ∩ S4 to S4-led (compare) with S2 (fit) secondary.** The Phase 2 nomination put
fit first; the evidence puts decision completion first.

**Segment evidence is thin and labelled as such.** Only **2 of 9** respondents (R03, R07) match
the strict staller definition, against a Phase 3 target of 5. Segment-specific claims in this
document carry that caveat. This is the single biggest weakness of the lock and the first thing
follow-up research should fix.

**S3 sale-watchers remain a control persona, not the audience** — unchanged from
[architecture.md](./architecture.md) Phase 4.

### Segment contract (interface only — implemented in Phase 5)

Revised from the architecture draft in two places, both driven by evidence:

```typescript
function matchesStalledShortlister(user: User): boolean {
  if (user.optedOut) return false;

  const recent = user.wishlistItems.filter((i) => i.addedWithinDays(30));
  // Was >= 3. Six of nine respondents hold only 1-5 saves in total,
  // so a three-item floor would exclude most of the real population.
  if (recent.length < 2) return false;

  // The stall itself: interest captured, decision not completed.
  const purchased = recent.filter((i) => i.purchasedWithinDays(30));
  if (purchased.length > 1) return false;

  // Was "any category with >= 3 items". Relaxed for the same reason:
  // two comparable options are enough to be stuck between them.
  const byCategory = groupByCategory(recent);
  return Object.values(byCategory).some((count) => count >= 2);
}
```

## 2. Product outcome

**Primary: Shortlist-to-decision rate** — the share of saved items that reach an explicit decision
(bought **or** deliberately dropped) within 30 days of being saved.

This is the **Decide** node of the metric tree, not **Resolve**. The change from the Phase 2
nomination is deliberate: comparison is the only lever confirmed by three independent signals,
while fit resolution is confirmed as a doubt but not as the decider.

**The margin is one person, and that matters.** Counting respondents once per node,
`phase-4/data/signals.json` puts Decide at 8/9 and Resolve at 7/9. Decide wins, but not by enough
to treat Resolve as a follow-up: the two must ship together, and the real case for Decide-first is
the unlock-versus-help evidence in §3 rather than this share.

| Layer | Measure |
|---|---|
| Business | W2P 30d |
| Product outcome (primary) | Shortlist-to-decision rate — Decide |
| Product outcome (secondary) | Uncertainty resolution rate — Resolve |
| Guardrail | Return rate must not rise; removals are a **success**, not a leak |

Counting a deliberate removal as a decision matters. A shopper who concludes "not for me" and
clears the item has been served, and their intent is no longer decaying inside the list. A metric
that only rewards purchases would push the product toward pressure tactics, which is the same
failure mode as a discount.

## 3. Root cause

> **A wishlist captures interest but offers no way to finish a judgement — neither "which of
> these is right for me" nor "is this worth what it costs". With no judgement aid available, the
> only decision tool the app does offer is a falling price, so intent parks itself on a sale that
> may never arrive inside 30 days.**

Price is therefore the **symptom of a missing capability**, not a demand for money. Three pieces of
evidence support that reading over "shoppers simply want it cheaper":

1. **Stated barrier and actual behaviour diverge.** Price leads what people *say* (5/9 on Q8, 7/9
   on Q10), but what they *do* is research and compare: reviews 8/9, customer photos 7/9, in-app
   comparison 6/9, size/fit reviews 5/9 — while only **2/9** wait for a sale (Q11). Exactly one
   respondent (R06) reports waiting for a sale as their *only* pre-purchase behaviour. People
   behave like unfinished decision-makers, not like bargain hunters.
2. **Every shopper who wants a discount asks for information instead when offered help.** This is
   the load-bearing finding, and it is checkable per respondent. Four people named
   *"Price drop/discount"* as the one thing that would unlock the purchase (Q12): **R01, R03, R05,
   R07.** On Q13 — where, by construction, [no option is a discount](./research/interview-guide.md) —
   all four ask for information: three of them (R01, R03, R07) want *"understanding whether the
   price is good"*, and R05 wants *"comparing it with alternatives"*. Not one is stranded by the
   absence of a coupon. Across the whole sample the unlock split is **4 monetary / 5 informational**,
   and R09 asks in Q12 for *"knowing whether I should buy now or wait"* — a value judgement
   requested as an unlock, with no money attached.
3. **Waiting is the default, not the goal.** "I want to wait for a better price" ties for the top
   reason to save (6/9, Q7), yet the same people hold few items and rarely act on sales. Waiting
   is what is left when no other move is available.

### Known challenge to this root cause

Both in-segment respondents (R03, R07) chose *"Price drop/discount"* on Q12. If price is genuinely
binding at current price for this segment, this root cause is wrong and the constraint conflict in
§7 becomes terminal.

The mitigating evidence is that **both of them also chose "understanding whether the price is
good" on Q13** — the two shoppers who most look like our segment ask for a price *verdict* the
moment a verdict is on offer. Two people is not proof of anything, and it is the reason §9 exists.

That challenge is **unresolved by design of the instrument**: the questionnaire never held price
constant, while brief questions 3 and 4 exist precisely to do so ("what stops you *even if the
price stayed the same*"). See [`docs/research/synthesis.md`](./research/synthesis.md) §3a. Until
that question is asked as written, we cannot distinguish a real price constraint from the easiest
available answer — and this lock is explicitly falsifiable on that point.

## 4. Existing workarounds

What shoppers already do, in order of measured frequency. Every workaround is evidence of the
missing capability: each one is a judgement being made *outside* the wishlist.

| Workaround | Frequency | Source |
|---|---|---|
| Read customer reviews | 8/9 | Q11 |
| Look at customer photos | 7/9 | Q11 |
| Compare items inside the app | 6/9 | Q11 |
| Hunt for size/fit reviews | 5/9 | Q11 |
| Leave for Instagram / YouTube try-ons | 2/9 | Q11 + `review-trust-gap` |
| Wait for a sale | 2/9 | Q11 + `sale-waitlist` |
| Search the product on Google | 1/9 | Q11 |
| Ask friends or family | 1/9 | Q11 + `social-validation` |
| Check other shopping apps | 1/9 | Q11 |
| Treat easy returns as the decision ("I can always return it") | — | `return-fear`, frequency 0.383 |

The scrape names the same behaviours in shoppers' own words. **These verbatims are labelled by
source.** Of the 30 distinct quotes across `themes.json`, exactly **2 carry live review ids** and
**28 are seeded fixtures** (`fix-*`) — a split the generator recomputes on every run
(`quotes.liveCount` / `illustrativeCount`). Only the live two are used as evidence; the rest are
**illustrative only**, per [problemstatement.md](./problemstatement.md) §4.1.

> *"from the last 1 month the service and product are getting worst in myntra. they send wrong
> size or damaged product…"* — Play Store, `playstore-83ec5f7a` (live)

> *"This is by far one of the worst shopping experiences… they misguided me about the delivery
> timeline…"* — App Store, `appstore-gb-2-13508351477` (live)

**There is no participant verbatim to quote.** The Phase 3 instrument was a closed-option form with
no free-text field, so it produced counts rather than sentences. Presenting a fixture line as a
participant quote would be the exact misrepresentation the brief forbids, so we do not.

Neither live verbatim is a clean statement of pre-purchase doubt, which is worth stating plainly:
**the public corpus is strongest on post-delivery disappointment and weakest on the hesitation
moment.** That asymmetry is why the questionnaire, not the scrape, carries the load in this lock.

## 5. User value

Finish the decision. Concretely:

- **A defensible choice** — knowing *why* this one and not the other two, rather than adding a
  fourth similar item (`comparison-paralysis`, 6/9 compare in-app).
- **A defensible price** — being able to tell whether the asking price is reasonable for what it
  is, which is the top requested help (4/9) and today has no answer except waiting.
- **Fewer open loops** — no second app, no WhatsApp poll, no YouTube detour before ordering.
- **Lower risk of being wrong** — fit and quality read from other shoppers' experience, at the
  moment of doubt rather than after delivery.

Confidence is the mechanism; the felt benefit is **closure**.

---

## 6. Business value

- **W2P 30d rises through decision completion, not margin.** Every point of shortlist-to-decision
  rate is a purchase that would otherwise have decayed, bought at full price.
- **Margin is protected.** The intervention is information. Nothing here trains shoppers to wait
  for EOSS, which is the compounding cost of the discount alternative.
- **Return-rate exposure falls** where fit doubt is resolved before ordering rather than through
  try-and-buy (`return-fear`, frequency 0.383).
- **Demand shifts out of sale windows.** If waiting is a default caused by missing judgement aid,
  supplying the aid moves volume into non-sale weeks.

All four are conditional on the root cause in §3 being right, and §3 states how it can be shown
wrong.

## 7. Decision tree — recorded outcome

The tree from [problemstatement.md](./problemstatement.md) §4.3, resolved against the evidence:

```
IF Phase 3 confirms a non-monetary Resolve and/or Decide blocker
   AND S3/price is not the dominant in-segment cause
THEN proceed with a confidence / decision-support MVP
   → Decide blocker CONFIRMED (comparison: 3 independent signals)
   → in-segment price dominance UNRESOLVED (2/2 chose a discount, n = 2,
     and price was never held constant)
   → so this branch cannot be taken cleanly

ELSE IF price is dominant even at current price
THEN do not build an incentive MVP; document the constraint conflict;
     pick another evidenced non-monetary problem or stop
   → TAKEN, in its non-terminal form: no incentive MVP, conflict documented
     below, and the evidenced non-monetary problem is decision completion
     plus value confidence

ELSE IF another node ranks higher
THEN rewrite Phase 5 scope before any coach contracts
   → ALSO TAKEN: Decide outranks Resolve, so Phase 5 scope is rewritten
     from fit-first to decision-completion-first
```

**Outcome: proceed, re-scoped — and explicitly not with an incentive.**

### Constraint conflict, stated plainly

The most-requested single unlock in this sample is a price drop (4/9, and 2/2 in segment). The
brief forbids monetary incentives as the core lever. That conflict is real and is **not** resolved
by pretending the data says something friendlier.

It is navigable for one reason, set out in §3: **all four discount-seekers, including both
in-segment respondents, switch to asking for information the moment the question is about help
rather than about an offer.** Value confidence is an information product; a discount is not. We
build the first and decline the second — and we record now that if follow-up research holds price
constant and price *still* dominates in segment, the correct conclusion is to stop, not to quietly
ship a coupon.

### What this gates for Phase 5

| Phase 5 decision | Locked position |
|---|---|
| Primary job | Complete the decision on a shortlist — Decide node |
| Secondary job | Resolve fit/quality doubt with other shoppers' evidence — Resolve node |
| **Required new surface** | **Value confidence** — "is this a fair price for this item, and should I decide now?" using non-monetary signals only |
| Forbidden | Discounts, coupons, price-drop alerts, EOSS nudges, urgency pressure |
| Framing to drop | "AI tells you which items are worth buying" — Q14 mean 2.89 with a flat zero |
| Guardrail | Deliberate removals count as success; return rate must not rise |

The comparison ritual already built in the storefront serves the primary job. **Value confidence
does not exist yet and is the largest evidenced gap in the product.**

## 9. How to falsify this lock

| Claim | Falsified by |
|---|---|
| Price is a symptom, not the cause | Holding price constant (brief Q3/Q4 as written) and price still dominating in segment |
| Decide outranks Resolve | In-segment shoppers naming fit information as the unlock more often than comparison help |
| Removals are a success | Removal-heavy cohorts showing lower W2P 30d than untouched cohorts |
| Value confidence is wanted | Shoppers ignoring a fair-price explanation while still converting on discounts |
| The segment exists at useful size | Targeted recruiting failing to find stalled shortlisters beyond R03 and R07 |

Every row is a measurement someone could run against this build. None requires trusting the
authors.
